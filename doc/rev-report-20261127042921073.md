## 4. 必须处理（P0）

### P0-001: FIFO TOCTOU 拒绝服务（`os.open` 缺 `O_NONBLOCK`）

- **位置**: `src/cat_mcp/fs/paths.py:44`（`_O_DIR_FLAGS` 定义）、`L298-303`（中间组件 `os.open`）
- **事实依据**: `_O_DIR_FLAGS = O_RDONLY | O_NOFOLLOW | O_CLOEXEC` 不包含 `O_NONBLOCK`。解析流程：stat→检查→`os.open(component, _O_DIR_FLAGS, dir_fd=current_fd)`。stat 和 open 之间存在 TOCTOU 窗口：中间组件目录条目可在 check 完成后被替换为 FIFO。缺少 `O_NONBLOCK` 时 `os.open()` 在 FIFO 上无限阻塞等待写入端打开。`ResolvedPath.open()`（L117-124）同样缺少 `O_NONBLOCK`。
- **推理**: 攻击者对工程目录有写权限时可用 `mkfifo` 替换目录项，导致服务永久挂起。
- **影响**: 单进程服务模式下线程/进程被永久占用，构成拒绝服务。
- **修复建议**: ① 在 `_O_DIR_FLAGS` 中添加 `O_NONBLOCK`，检测到 `ENXIO`（FIFO 无写端）时转 `CatError(UNSAFE_PATH)`；② `ResolvedPath.open()` 同样添加 `O_NONBLOCK`；③ 或者用 `os.open` 后立即 `os.fstat` 二次校验文件类型。

## 5. 建议处理（P1）

### P1-001: 未知 errno 默认映射为 `PATH_OUT_OF_BOUNDS`

- **位置**: `src/cat_mcp/fs/paths.py:508-509`
- **事实依据**: `else` 分支将所有未显式映射的 OSError errno 映射为 `PATH_OUT_OF_BOUNDS`。未映射的包括 ENAMETOOLONG、EMFILE/ENFILE、EROFS、EIO、ENOTEMPTY、EXDEV 等。
- **推理**: `PATH_OUT_OF_BOUNDS` 语义是「路径越界」，而 EMFILE（fd 耗尽）与此完全不相关。客户端收到「路径越界」后会检查路径而找不到原因。
- **修复建议**: 默认 fallback 改为 `ErrorCode.OPERATION_FAILED`，并补充映射 ENAMETOOLONG→INVALID_PATH、EROFS→FORBIDDEN、EMFILE/ENFILE→LIMIT_EXCEEDED。

### P1-002: `follow_symlinks` 构造参数死代码

- **位置**: `src/cat_mcp/fs/paths.py:164-177`（`__init__`）
- **事实依据**: 构造参数 `follow_symlinks` 接收并存入 `self._follow_symlinks`，但在 `resolve()`/`_resolve_root()`/`resolve_parent()` 中从未被引用。
- **推理**: 构造时传 `follow_symlinks=True` 与 `False` 行为完全等价，对调用方产生误导。
- **修复建议**: 删除构造参数和 `self._follow_symlinks`（按逐操作控制模式，即当前 `ResolvedPath.open/stat` 的独立参数模式）。

### P1-003: 异常泄露工程根绝对路径

- **位置**: `src/cat_mcp/fs/paths.py:174-175`
- **事实依据**: `raise ValueError(f"project_root is not a directory: {resolved}")` — `resolved` 是 `os.path.realpath()` 返回的规范绝对路径。不是 CatError，不经错误映射。
- **推理**: 设计文档要求「不泄露主机绝对路径」。若 `__init__` 在请求过程中被调用，绝对路径可达客户端。
- **修复建议**: 改为 `raise CatError(ErrorCode.INTERNAL_ERROR, "Project root configuration error")`。

### P1-004: 目录遍历深度未限制

- **位置**: `src/cat_mcp/fs/paths.py:257`（for 循环）；设计文档配置段 `directory_depth: 8`
- **事实依据**: 设计文档 `directory_depth` 默认值为 8，但代码无深度上限检查。10000 组件路径触发 10000 次 stat+open 系统调用。
- **推理**: 配置合同未在代码中落地。虽受 PATH_MAX 约束（macOS 1024, Linux 4096），但已可造成可观的资源开销。
- **修复建议**: 在循环入口加深度上限检查：`if len(parts) > 64: raise CatError(ErrorCode.INVALID_PATH, ...)`。
